# Attendance Table Archival Strategy (5M+ Rows)

## 📌 Problem
As `attendances` table grows beyond 5 million rows, operational efficiency (INSERT/UPDATE/INDEX) decreases. 
Reports spanning large date ranges become slower.

## 🚀 Strategy: Yearly Partitioning (Application Level)

Instead of complex Database Partitioning (which varies by DB Engine), we implement **Logical Sharding by Year**.

### Architecture
1. **Active Table:** `attendances`
   - Holds current year's data.
   - Used for daily operations (Check-in, validation).
   - Hot path (High Write, High Read).

2. **Archive Tables:** `attendances_YYYY` (e.g., `attendances_2025`)
   - Holds historical data.
   - Optimization: **Read-Optimized**. Can have additional indexes for reporting without penalizing writes.
   - Immutable mostly (except corrections).

### 🛠️ Components

#### A. Artisan Command (`attendance:archive`)
- **Action:** Moves data older than current year to `attendances_YYYY`.
- **Method:** `INSERT INTO ... SELECT` + `DELETE` in chunks.
- **Schedule:** Run annually (Jan 1st) or Monthly.

```bash
php artisan attendance:archive --year=2025
```

#### B. Query Service (`AttendanceArchiveService`)
- intelligently detects which tables to query based on `StartDate` and `EndDate`.
- Uses `UNION ALL` to combine results efficiently.
- Benefits:
  - If report is for *This Month*: Only queries small `attendances` table.
  - If report is for *Last Year*: Only queries `attendances_2025`.
  - If report spans years: Unions them.

### ⚡ Optimization & Indexes

1. **Primary Reporting Index (Crucial for Range Queries)**
   ```sql
   CREATE INDEX idx_school_date_report ON attendances (school_id, attendance_date);
   CREATE INDEX idx_student_date_history ON attendances (student_id, attendance_date);
   ```
   *Why?* Most queries filter by `school_id` AND a date range. This index allows the DB to scan only the relevant rows without sorting.

2. **Archive Table Optimization**
   Archive tables should have the **Same Indexes** as active table to support identical query performance.
   Optionally, you can add *Covering Indexes* (including `status`, `time`) to avoid looking up the heap.

### ⚠️ Validations & Risks

- **Foreign Keys:** Archive tables should ideally **DROP** foreign key constraints to `users` or `schools`. 
  *Reason:* If a user is deleted in 2027, their 2025 attendance record should remain as historical proof.
- **Global ID:** The `id` column might collide if not careful.
  *Solution:* We rely on `AUTO_INCREMENT` continuing. When moving data, we preserve the original `id`.
  Since we DELETE from source, there is no ID overlap.

### 📋 Sample Query Pattern (Optimized)

```sql
-- Generated by Service for Range: 2025-12-01 to 2026-01-31

(SELECT student_id, status, attendance_date FROM attendances_2025 
 WHERE school_id = 1 AND attendance_date >= '2025-12-01')
UNION ALL
(SELECT student_id, status, attendance_date FROM attendances 
 WHERE school_id = 1 AND attendance_date <= '2026-01-31')
```
This query hits the index on both tables and merges results without overhead.
